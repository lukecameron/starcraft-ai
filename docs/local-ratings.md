# Local ratings

The dashboard estimates relative strength from explicitly selected real games. These are **uncalibrated local league estimates**, not BASIL ratings. An original bot, a port and an improved fork retain their own identities; no upstream rating is copied to a local binary.

`config/local-ratings.json` lists eligible experiments and the SHA-256 of each reviewed terminal manifest. Add a reviewed run only after checking both replay hashes, parsing both with screp, confirming normal opposing results and checking the engine diagnostic logs. The exporter independently rejects incomplete or conflicting results, missing replay bytes, hash mismatches, unsupported latency/learning state, diagnostic bots and repeated exact scenarios. Failures remain visible. An unreviewed run cannot silently change a rating. A clean Cloudflare build keeps the reviewed published snapshot because local replays are deliberately absent from Git.

A rating node consists of the exact module SHA, race and packaged AI configuration hashes. The comparison regime includes launcher, engine library and game-data hashes, platform, latency, learning state and timeout/adjudication settings. Connected components are displayed separately. Changing any bot code or configuration creates a new node and never inherits its predecessor's games.

For log-strengths θ, the model uses `P(i beats j) = logistic(θ_i − θ_j)` and independent Gaussian priors with standard deviation equivalent to 400 Elo. `400 / ln(10)` converts log-strength differences to Elo. The fitted value is the maximum a posteriori estimate. A Newton solve finds it, and the inverse posterior Hessian supplies a **Laplace approximation** to covariance. Displayed 95% intervals use the covariance of each contrast with the reference, including uncertainty in both players. They are not exact posterior quantiles or frequentist confidence guarantees.

The selected ZZZK build is assigned 1000 as a display coordinate. Its zero-width interval means it is the reference for subtraction, not that its playing strength is known perfectly. If ZZZK is absent from a disconnected component, that component uses its own reference. Scores from different components cannot be compared. Histories accumulate evidence for an unchanged exact build against an unchanged reference; improvements are new builds, not continuations of an old curve.

The default prior gives finite estimates for sweeps while retaining broad uncertainty. The dashboard also exposes results under 200 and 800 Elo prior standard deviations. A large change means the data do not yet determine the estimate. These are actual-game likelihoods with an explicit prior, not fictitious wins or inherited ladder observations.

The model assumes transitive strength and conditionally independent outcomes. Map effects, starting positions, style cycles, related bot families, time-budget nondeterminism and repeated map/slot pairs can violate these assumptions. Sparse intervals therefore describe this model and cohort, not generalization to the ladder. Pairwise records, map/opponent coverage, failures and provenance matter alongside the scalar estimate. Two maps and a handful of games are an initial calibration, not a precise strength claim.

Method references: [Whelan, Prior Distributions for the Bradley–Terry Model of Paired Comparisons](https://arxiv.org/abs/1712.05311) discusses independent Gaussian priors on log strengths; [Mattos and Ramos, Bayesian paired comparison with the bpcs package](https://pmc.ncbi.nlm.nih.gov/articles/PMC9374650/) describes Bayesian paired comparisons and uncertainty. Our small standard-library solver and Laplace approximation are project implementation choices, not use of the bpcs package.

Validation includes balanced outcomes, sweeps, label/order invariance, disconnected graphs, an independent dense one-dimensional MAP grid and finite-difference curvature, evidence deduplication and build/regime separation. Validation of a numerical model does not validate the quality of a bot port or calibrate it to BASIL.

## Cohort coverage

The current-engine league has 36 reviewed games and five exact build/race nodes: 24/24 in the four-map cohort and 12/12 in the missing-edge extension. The historical engine retains 9/12 valid games in a separate regime. Cohort labels and expected counts are display metadata: additional cohorts in the same exact regime pool cumulative evidence, while actual engine/settings changes create separate components. Each configured cohort has an explicit `current` flag; labels do not determine statistical inclusion. See [the current result](evaluations/local-calibration-v3/RESULT.md).
