# McRave goal-assignment performance

The preserved Destination timeouts isolate the cost to the McRave process. In runs `20260920T025132-cb24a640d358` and `20260920T025316-90e77ce69d14`, McRave used 115.5 and 115.2 user CPU seconds with about 489 MB peak RSS. The synchronized UAlbertaBot processes used 13.7 seconds and about 55 MB. Reversing player assignment retained the same process-level split.

The preregistered profile at `artifacts/experiments/mcrave-timeout-profile-v1` sampled the exact McRave launcher for ten seconds late in the seed-3001 game. Of 7,780 main-thread samples, 3,701 (47.6%) were under `Goals::onFrame`, 3,560 (45.8%) were under its `assignNumberToGoal` ground-distance call, and 3,426 (44.0%) ended in BWEM nearest-area breadth-first search. The source path assigns all eligible zerglings to a distant expansion goal. It repeatedly scans the unit container and recalculates the same fixed goal-to-unit ground distances after each selected unit becomes ineligible.

The candidate patch caches those distances only within one `assignNumberToGoal` invocation. It retains the original unit-container order, strict `<` comparison, eligibility check before each selection, and assignment mutation. It returns after the existing cached-assignment pass when the remaining count is zero or negative, matching the original zero-iteration loop without calculating distances. Flying units retain the original Euclidean helper. No value survives the invocation or frame. The check in `ports/mcrave/goal_assignment_equivalence.py` first verifies the relevant contracts in the actual `Util.h` and `Goals.cpp` sources, then compares the original repeated scan with the cached scan across 10,000 ordered randomized cases. Cases include initially ineligible units, equal-distance ties, `DBL_MAX`, infinity, NaN, and requests larger than the candidate set. `getClosestUnitGround` has no hidden existence or radius filter: it applies the supplied predicate, calculates `BWEB::Map::getGroundDistance`, and selects with strict `<`. BWEB returns `DBL_MAX` for invalid or disconnected endpoints, which neither implementation selects because the initial best value is also `DBL_MAX`.

The preregistration file's APFS birth, modification, and change timestamps are all `2026-09-20T03:07:48Z`, before the candidate launch at approximately `03:08:48Z`. Its original manually entered `created_at` value of `03:09:00Z` was wrong and was corrected to the filesystem timestamp after review; the experiment result does not rely on the erroneous value.

The candidate is frozen at `artifacts/builds/0c351cc92ba662e03808ebe499ae8afdefe2066dd81e92b94f20f9c74cad4a8a/McRave.dylib`. Its official BWAPI 4.4 object build passed all 114 translation units. The exact seed-3001 candidate run is `artifacts/runs/20260920T030848-ac4ea9f6a371/game-0001/manifest.json`. It reached frame 27,840 in 120.08 seconds, or 231.84 durable logical frames per second. The preserved unoptimized seed-3001 timeout reached frame 22,800 at 189.89 durable frames per second, so measured throughput increased 22.1%. The baseline used an earlier engine build whose later patch concerned launcher lifetime handling, so this is not a binary-identical engine comparison. Relative to the separately sampled baseline run on the candidate engine, throughput increased 30.2%, though sampling overhead makes that comparison secondary.

The candidate game timed out and therefore produced no replay or verified outcome. Its partial diagnostics recorded 59 drones, 165 zerglings, and eight hatcheries. The baseline and candidate selected different McRave openings despite the engine seed because McRave's learning selection uses process-global `rand()` outside the controlled engine RNG. Unit populations and game trajectories therefore differ, and the observed throughput is useful performance evidence rather than an exact paired causal estimate. The configured baseline remains unchanged, and this result does not support a strength claim or promotion.
